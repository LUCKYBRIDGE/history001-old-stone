# 1. 최종 판정

## **GO — Stage 06 기술 설계에 진입 가능**

현재 01~05는 큰 방향을 다시 설계할 필요가 없다.

프로젝트의 핵심은 단계가 진행되는 동안 일관되게 유지되었다.

- 설명·퀴즈보다 **상황을 먼저 경험**한다.
- 구석기 생활을 사냥 하나로 대표하지 않는다.
- 프로젝트의 핵심 단위는 **하나의 공동체가 보내는 하루**다.
- 사냥·채집·머무는 역할은 서로 다른 역사적 경험을 책임진다.
- 이동 생활은 처음부터 정답으로 알려주지 않고 앞선 경험이 누적된 뒤 이해하게 한다.
- 실패는 GAME OVER가 아니라 생활의 불확실성을 체험하는 정상적인 결과다.
- 공통 시스템은 역할을 연결하지만 역할 고유 플레이 문법을 강제하지 않는다.

따라서 지금 필요한 것은 기획 확장이 아니라 **검증 과정에서 발견된 세 개의 모호성을 제거하고 실제 프로토타입으로 넘어가는 것**이다.

이 세 가지는 `docs/05_ROLE_EXPERIENCE_MAP.md` v2에 반영했다.

# 2. Stage 01 — PROJECT CORE 검증

## 판정

**유지 — 상위 방향 수정 불필요**

## 잘 설계된 점

- 프로젝트를 `구석기 시대를 설명하는 웹`이 아니라 **생활 속에 잠시 들어가 보는 역사 체험형 웹게임**으로 정의한다.
- 사실 암기보다 `상황을 경험 → 이유를 생각 → 다른 사람의 생활과 연결 → 역사적 생활상을 이해`하는 흐름을 우선한다.
- 사냥·채집·머무는 사람을 주요/보조 관계가 아닌 동등한 관점으로 정의한다.
- `먼저 개발되는 역할 ≠ 더 중요한 역할` 원칙이 명확하다.
- `[교과서] / [재구성] / [게임]`의 구분을 프로젝트 최상위에서 관리한다.
- 이동 생활을 설명의 출발점이 아니라 체험의 결과로 둔다.

## 검증 결론

01은 현재 프로젝트의 헌법 역할을 충분히 수행한다.

이후 구현이 01과 충돌할 경우 01을 쉽게 수정하기보다 **구현 아이디어가 프로젝트 목적에서 벗어난 것은 아닌지 먼저 점검**한다.

# 3. Stage 02 — EXPERIENCE STRUCTURE 검증

## 판정

**유지 — 05 v2에서 실행 원칙을 구체화**

## 잘 설계된 점

전체 체험을

**공통 아침 → 세 역할의 서로 다른 하루 → 공통 저녁 → 며칠 변화 → 이동 → 새 거처 → 역사 개념화**

로 묶었다.

특히

- 공통 경험 층
- 역할 고유 경험 층

을 구분하고

> **공통 구조는 역할을 담는 그릇이지, 세 역할을 같은 방식으로 플레이하게 만드는 틀이 아니다.**

라는 원칙을 둔 것이 이후 기술 설계에도 매우 적합하다.

또한 학생이 역할을 하나씩 경험하면서 같은 하루를 더 넓게 이해해야 한다는 방향이 이미 포함되어 있다.

## 검증에서 발견된 모호성

`학생이 세 역할을 어떤 방식으로 모두 경험하는가`가 실제 앱 구현 규칙 수준에서는 충분히 잠겨 있지 않았다.

## 리비전

02의 전체 구조 자체는 수정하지 않고, 하위 시스템 경계 문서인 05 v2에서 다음을 명확히 했다.

# **최종 체험의 기본값은 한 학생이 사냥·채집·머무는 세 관점을 모두 경험한다.**

다만 같은 아침·설명을 세 번 반복하지 않고, 두 번째·세 번째 역할은 같은 하루의 빈칸을 새 관점으로 채우는 방식으로 설계한다.

역할 순서와 화면 전환 UX는 프로토타입에서 검증한다.

# 4. Stage 03 — HUNT STORY 검증

## 판정

**유지 — 핵심 서사 구조 적절**

## 잘 설계된 점

사냥을

`동물을 잡는 액션`이 아니라

**찾고 → 시도하고 → 결과를 확신하지 못하고 → 위험을 살피고 → 돌아오는 생활 경험**

으로 설계했다.

특히

# **“사냥의 끝은 동물을 잡는 순간이 아니라, 성공하든 실패하든 사람들에게 무사히 돌아오는 순간이다.”**

라는 구조는 사냥 성공 중심의 게임화를 효과적으로 막는다.

`해가 지기 전에 돌아와.`라는 모티프가 나중 머무는 사람의 `왜 아직 돌아오지 않을까?`로 연결될 수 있는 점도 같은 하루를 세 관점으로 묶는 데 효과적이다.

## 구현 시 주의

자연 속 인간의 취약함을 보여주는 장치가 `매번 포식자가 등장하는 이벤트`로 고정되면 구석기 생활에 대한 과도한 이미지를 만들 수 있다.

따라서 구체 구현에서는 위험한 흔적, 낯선 소리, 지형, 거리, 어두워지는 시간 등 다양한 조건으로도 취약함을 표현할 수 있도록 열어 둔다.

03의 기준 서사 자체는 수정할 필요가 없다.

# 5. Stage 04 — HUNT PLAYFLOW 검증

## 판정

**유지 — Vertical Slice 기준으로 충분**

## 잘 설계된 점

- 공통 아침 / 사냥 고유 플레이 / 공통 저녁의 경계가 명확하다.
- `[공통 경험]`과 `[사냥 고유 경험]`을 분리한다.
- 사냥의 플레이 리듬을 채집·머무는 역할에 복제하지 말라는 규칙이 명시되어 있다.
- 모든 장면에 선택이나 조작을 강제로 넣지 않는다.
- 성공과 실패 모두 귀환과 공통 저녁으로 이어진다.
- 사냥만으로 이동 생활의 이유를 완성하지 않는다.

## 구현 시 주의

04의 상세 장면은 `반드시 모두 구현해야 하는 장면 목록`이 아니라 **학생에게 필요한 경험 beat 목록**으로 취급한다.

프로토타입에서 장면이

`읽기 → 다음 → 읽기 → 다음`

으로 반복되거나 새로운 경험을 만들지 못한다면 합치거나 삭제한다.

04 자체를 추가로 확장하지 않는다.

# 6. Stage 05 — ROLE EXPERIENCE MAP 검증

## 판정

**리비전 — v1 → v2**

Stage 05의 역할 분리는 전반적으로 매우 좋았지만 세 가지를 보정해야 했다.

---

## 리비전 A — 학생은 세 역할을 모두 경험한다

### 기존 위험

세 역할이 동등한 관점이라고 정의되어 있어도 기술 구현에서 `역할 하나 선택 → 엔딩` 구조로 축소될 수 있었다.

### v2 결정

# **최종 체험의 기본값은 한 학생이 세 역할을 모두 경험한다.**

다만 세 역할을 세 개의 독립 게임처럼 반복하지 않는다.

- 같은 공동체
- 같은 하루
- 같은 사건

을 다른 위치와 의미에서 다시 보며 하루의 빈칸을 채우게 한다.

Stage 06에서는 세 역할 경험 진행 상태를 지원하되 특정 역할 순서를 하드코딩하지 않는다.

---

## 리비전 B — 채집의 `자원 감소` 표현 보정

### 기존 위험

`가까운 자원이 줄어든다`를 너무 직접적으로 구현하면 학생이

> 며칠 동안 주변 먹을거리를 모두 소비해서 이동했다

와 같은 단순 인과로 이해할 수 있다.

### v2 결정

채집의 핵심 표현을

# **“가까운 곳에서 먹을 것을 계속 똑같이 쉽게 얻을 수 있는 것은 아니다.”**

로 보정했다.

학생은 같은 장소를 다시 이용했을 때 이전과 다른 결과를 느끼고 점차 더 넓은 범위를 살펴본다.

구체적 자원 감소 상황은 `[재구성]`·`[게임]`으로 관리하고 보편적인 역사 사실처럼 단정하지 않는다.

---

## 리비전 C — 머무는 역할은 독립적인 이동 원인이 아니다

### 기존 위험

사냥 / 채집 / 머무름 각각이 `이동 이유 하나씩`을 제공해야 역할이 동등하다고 해석할 수 있었다.

하지만

`밖의 사람들이 더 늦게 돌아온다`

는 변화는 사냥·채집의 생활 반경이 넓어지면서 거처 쪽에서 경험하는 결과로 보는 편이 구조상 더 자연스럽다.

### v2 결정

머무는 역할은

# **사냥·채집의 넓어진 생활 반경이 공동체 전체에 주는 시간적·정서적 부담을 거처의 시점에서 경험시키는 역할**

로 재정의했다.

역할 동등성은 `독립적인 이동 원인을 하나씩 갖는가`가 아니라 **전체 이해에서 대체할 수 없는 관점을 갖는가**로 판단한다.

# 7. 현재 앱 방향 검증

현재 01~05가 지향하는 앱은 다음과 같다.

```text
하나의 공동체
      ↓
공통 아침
      ↓
같은 하루의 세 관점
 ┌────┼────┐
사냥  채집  머무름
 └────┼────┘
      ↓
공통 저녁
      ↓
“각자의 하루가 하나의 생활이었구나”
      ↓
며칠의 압축된 변화
      ↓
먹을 것을 구하는 생활 반경이 넓어짐
      ↓
그 부담이 공동체 전체에 커짐
      ↓
“이곳에서 계속 살아갈 수 있을까?”
      ↓
이동
      ↓
새로운 곳에서도 생활은 쉽지 않음
      ↓
이동 생활 개념화
```

이 구조는 현재 프로젝트의 교육적 목표와 역할 설계를 가장 잘 보존한다.

# 8. Stage 06에 넘길 필수 Guardrail

기술 설계는 다음을 반드시 만족해야 한다.

1. **Common Shell과 Role Feature를 분리한다.**
2. Common Shell은 역할 진행을 연결하지만 역할별 게임 루프를 규정하지 않는다.
3. 한 학생이 세 역할을 모두 경험할 수 있는 진행 상태를 지원한다.
4. 특정 역할 순서는 하드코딩하지 않는다.
5. 공통 저녁을 단순 결과표 컴포넌트로 축소하지 않는다.
6. Hunt 구현 편의를 위해 Gather/Camp 인터페이스를 Hunt 구조에 맞추지 않는다.
7. 역할 결과는 점수보다 `공통 저녁과 이후 변화에 필요한 의미 있는 상태`만 전달한다.
8. 최종 이미지 없이도 플레이 구조를 먼저 검증할 수 있어야 한다.
9. 기획 문서의 장면 수를 코드 장면 수와 1:1로 강제하지 않는다.
10. 학생 테스트 전까지 역할 플레이 시간과 인터랙션 수를 기계적으로 동일하게 맞추지 않는다.

# 10. 최종 결론

## **01~05의 앱 방향은 유지한다.**

현재 프로젝트는

- 역사 사실을 퀴즈로 재확인하는 앱이 아니라
- 구석기 생활의 조건을 서로 다른 관점에서 경험하고
- 역할별 불확실성과 공동체성을 연결한 뒤
- 이동 생활을 `이유가 있는 생활 방식`으로 이해하게 하는 앱

으로 일관되게 설계되고 있다.

Stage 06부터는 새로운 상위 기획을 더 쌓기보다 **실제로 작동하는 기술 구조와 Vertical Slice를 만들고 플레이를 통해 가설을 검증하는 것**이 더 중요하다.

따라서 이번 검증 이후 판정은

# **GO TO STAGE 06**

이다.
